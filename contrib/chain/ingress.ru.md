# Вход WireGuard или VLESS

Один проект Compose обслуживает один профиль с одним ключом WireGuard или UUID VLESS. Выбранный режим применяется ко всем TCP/UDP-потокам профиля. Отдельный проект и другой внешний порт позволяют выдать тому же пользователю второй маршрут. Передача полезной нагрузки поддерживает IPv4. В WireGuard маршрут IPv6 включён в клиентский туннель и блокируется на входе.

На узле сборки укажите проверенный образ Xray-core с digest для нужной архитектуры и путём /usr/local/bin/xray. Контекст сборки ограничен каталогом адаптера. На узле исполнения нужны Linux, поддержка WireGuard в ядре, iptables IPv4/IPv6 с owner и conntrack, NET_ADMIN внутри сетевого пространства проекта и Compose v2.

```sh
export XRAY_IMAGE=ghcr.io/xtls/xray-core:25.12.8@sha256:3041edb72f2b2cab0628f2bc22e83b0300a60aba3c1ee0a7264bd98997e01194
docker build --build-arg XRAY_IMAGE="$XRAY_IMAGE" -f contrib/chain/Dockerfile.ingress -t anet-ingress:local contrib/chain
```

Выпустите профиль на доверенной машине с Python 3 (для WireGuard нужен пакет cryptography). Каталог назначения должен быть новым, за пределами checkout, в приватном каталоге на файловой системе с поддержкой прав POSIX. В --host укажите адрес входа, в --port опубликованный порт. В --dns укажите IPv4 DNS, достижимый с выбранного выхода.

```sh
python3 contrib/chain/issue-ingress.py wireguard /srv/anet/wg-a --host vpn.example.org --port 51820 --dns 1.1.1.1
python3 contrib/chain/issue-ingress.py vless /srv/anet/vless-b --host vpn.example.org --port 8443 --dns 1.1.1.1
```

Для VLESS положите сертификат с цепочкой и приватный ключ для этого имени в server/tls.pem и server/tls.key с правами 0600. Каталог server и его содержимое должен читать UID 0 контейнера (для rootless это пользователь демона). Передавайте клиенту только client.conf или client.uri по защищённому каналу. На iOS импортируйте конфигурацию в WireGuard либо ссылку в клиент VLESS с TLS. Сертификат должен проходить обычную проверку доверия и имени.

Добавьте значения в окружение установленного проекта. Пример для WireGuard через ANet из корня репозитория:

```sh
export VPN_BIND=127.0.0.1
export INGRESS_IMAGE=anet-ingress:local INGRESS_PROTOCOL=wireguard INGRESS_PATH=chain
export INGRESS_DIR=/srv/anet/wg-a/server INGRESS_PORT=51820 INGRESS_TARGET=51820/udp
docker compose -p wg-a -f contrib/deploy/compose/compose.yaml -f contrib/deploy/compose/chain.yaml -f contrib/chain/ingress.yaml up -d
```

Для VLESS задайте INGRESS_PROTOCOL=vless, INGRESS_DIR=/srv/anet/vless-b/server, INGRESS_PORT=8443 и INGRESS_TARGET=8443/tcp. В режиме одного выхода задайте INGRESS_PATH=direct и уберите chain.yaml. Используйте собственные STATE_DIR и параметры основного VPN-сервера для каждого проекта. Для локальной проверки установите VPN_BIND=127.0.0.1 и уникальный VPN_PORT для базового сервера. Новый порт адаптера публикуется на 127.0.0.1 по умолчанию. Для подключения с телефона задайте INGRESS_BIND равным выбранному адресу узла и откройте соответствующий TCP/UDP-порт. Контейнеры в сетях проекта могут обращаться к слушателю напрямую.

WireGuard передаёт внутренние пакеты через правило для интерфейса wg-profile. VLESS принимает TLS на TCP 8443, запускается под отдельным UID 17777 и маркирует исходящие пакеты этого UID, включая DNS. В цепочке таблица 177 направляет их в anet-uplink. Правила фильтра ограничивают выход пакетов этим интерфейсом. Обратные пакеты внешнего сеанса TLS возвращаются клиенту обычным путём.

Для проверки с каждого клиента передайте TCP-запрос и UDP-датаграмму на подконтрольный приёмник и сравните наблюдаемый IP с адресом ожидаемого выхода. Повторите при остановленном исходящем клиенте цепочки. Пакеты цепочного профиля должны перестать приходить, прямой профиль в другом проекте должен продолжить работу. Проверьте запрос по доменному имени, повторное подключение и оба активных профиля одновременно.

Чтобы отозвать профиль, выполните down с теми же -p и -f для его проекта. Удаление сетевого пространства убирает также ключи ядра WireGuard. Для перевыпуска создайте новый каталог, замените INGRESS_DIR и выдайте новый клиентский файл. Храните исходный клиентский файл и резервные копии как секреты.

## Приёмка 22 ноября 2026

На Debian linux/amd64 с rootless Docker проверены настоящий kernel WireGuard и Xray 25.12.8 с проверкой TLS-сертификата на клиенте. В изолированной сети стенда получатель наблюдал 172.22.0.4 для прямого профиля и 172.22.0.3 для цепочного при передаче TCP и UDP через каждый адаптер. После остановки uplink цепочного профиля получатель не зарегистрировал контрольную UDP-датаграмму, TCP-ответ отсутствовал. После запуска uplink оба протокола восстановились на прежнем выходе. Импорт на физическом iPhone и наблюдение публичного адреса внешним получателем требуют отдельного прогона.

Для повторения установите INGRESS_IMAGE и PYTHON_IMAGE. Запустите contrib/deploy/tests/chain.py accept с --hold-until, затем вызовите test_ingress_live.py с параметрами --entry-container, --entry-ip, --network, --target-ip, --exit-ip и --path для нужного профиля. Для проверки потери цепочки добавьте --outage-uplink и --target-container с именами временных контейнеров этого стенда. Тест требует Python с cryptography, OpenSSL и rootless Docker на машине запуска. В изолированном проекте адресный диапазон 10.79.0.0/30 зарезервирован за клиентом WireGuard.
