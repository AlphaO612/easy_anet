На одном компьютере WSL2 с ядром 6.18.58.1 клиент, сервер и приёмник запущены в трёх сетевых пространствах имён. Клиент установил QUIC-сеанс с сервером своей версии и передал через TUN TCP- и UDP-запросы. Сервер заменён на бинарник из images.tar. После повторного запуска клиент с тем же файлом снова передал оба запроса. Приёмник вернул ожидаемый адрес SNAT 192.0.2.1 и случайную строку каждого запроса. Для минимальных TOML исходным сервером служила сборка этапа 3.

В шаблонах из zip до первого запуска подставлены стендовые ключи, адрес QUIC и manual_routing. Между серверами байты файла сохранены. SHA-256 тестового конфига 0.7.2 был `e6e73e70f8eb99157473524c7a430aef5fc921134bd8b7b1ddd3c9aa59c5674c`, для 0.7.3 — `7f7f7c27975f08487e2a991a8b174d068d85ec8920c9d8680f06dcbe09ad00e0`. При воспроизведении тест генерирует свежие временные ключи.

## Воспроизведение и предварительный просмотр обновления

Из корня репозитория передайте в тест бинарники и конфиг из официальных архивов выпуска. В качестве `NEW_SERVER` используйте бинарник из проверяемого образа. Параметр `--library` нужен на машинах, где бинарники требуют более новой glibc. Он принимает каталог библиотек из образа, включая загрузчик `ld-linux-x86-64.so.2`.

```sh
python3 contrib/deploy/tests/test_client_upgrade_live.py \
  --before "$OLD_SERVER" --after "$NEW_SERVER" --client "$OLD_CLIENT" --template "$OLD_CLIENT_TOML"
manifest=contrib/deploy/compatibility/server-558c9ee3.json
python3 contrib/deploy/scripts/release.py check-client "$manifest" anet-client-cli-0.7.2-linux-amd64 upstream-0.7.2-toml quic
python3 contrib/deploy/scripts/release.py pre-upgrade "$manifest" "$ISSUED_LEDGER"
```

На отдельной SQLite-базе выдач шесть проверенных сочетаний дали `supported: true` и код 0. После добавления выдачи для непроверенной комбинации 0.6.0 CLI показал соответствующий профиль с `supported: false` и вернул код 2. Для следующей замены серверного бинарника проверку нужно повторить. При неудачной приёмке восстановите прежний образ с прежним состоянием установки и сверенным файлом клиента.

## eBPF на отдельном стенде

На том же ядре Linux выполнен отдельный прогон с eBPF-вариантом официального сервера v0.7.3, SHA-256 `98eec88714b47461365f1d2045a8c0c776785e40351178917b39e9bd9495b14c`. Исходники `anet-ebpf/src`, `anet-ebpf-common/src` и `anet-server/src/shaper.rs` совпадают с веткой на момент проверки. Сервер из tar 8715d02 собран с отключённой возможностью `ebpf-shaper`.

[Стенд шейпера](../tests/test_shaper_live.py) создаёт отдельные сетевые пространства для сервера, клиента и приёмника. Локальный HTTP-сервис возвращает авторизацию только для тестового ключа и задаёт ограничение 2000 кбит/с. Один бинарник сервера последовательно запущен с выключенным и включённым шейпером. В обоих случаях CLI 0.7.3 передал TCP и UDP через QUIC. При включении на TUN созданы qdisc fq и XDP в режиме SKB, сервер подтвердил подключение tc_egress и xdp_ingress, а затем установку ограничения на IP этого клиента.

| Измерение у получателя | Без шейпера | Лимит 2000 кбит/с |
| --- | ---: | ---: |
| Загрузка, Мбит/с | 514,10 | 1,98 |
| Отдача, Мбит/с | 385,43 | 2,00 |

Это по одному замеру в каждом направлении, длительность отправки — четыре секунды. Для воспроизведения на отдельном Linux-хосте со включёнными BPF и TUN выполните команду с правами, позволяющими загрузить программы в ядро. Тест сам создаёт изолированные mount и network namespaces.

```sh
sudo python3 contrib/deploy/tests/test_shaper_live.py \
  --server "$SHAPER_SERVER" --client "$OLD_CLIENT" --kbps 2000
```

По завершении тест останавливает процессы и освобождает их интерфейсы и BPF-программы. Рабочий профиль iPhone и Docker-проекты в прогоне не участвовали.
