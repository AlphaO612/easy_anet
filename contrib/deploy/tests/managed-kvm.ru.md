# Приёмка оркестрации профилей в KVM

Одна отдельная Debian 12 VM, один физический хост, rootless Docker 29.10.0. Стенд состоял из панели с PostgreSQL, Prometheus и Blackbox Exporter, двух зарегистрированных узлов, отдельных Compose-проектов входных профилей и временных клиентов и приёмников. Семейство адресов IPv4. Проверялись адреса SNAT пакетов на двух изолированных Docker bridge. Между входным профилем и выходным сервером работал настоящий туннель ANet QUIC. Для отдельного сетевого адреса гостя использовался dummy-интерфейс 198.18.253.1/32, поскольку подсеть QEMU пересекалась с подсетью транспорта rootless Docker.

На целевой панели проверены образы auth `sha256:664189809df69414ebaa58a07d3b4f9dcad887b21112efa7580a803fd6f4d307` и WebUI `sha256:ed26f089d6e7aca81e57b7292a2615deeb8c973669aa40c8be456b1b3134fe1d`. Сервер использовал бинарник из [поставки 8715d02](../compatibility/README.ru.md). Входной узел получил учётные данные при регистрации. Его системный сервис пользователя Docker запустил контроллеры по полученной подписанной топологии без административной сессии. Выходной сервер был зарегистрирован с идентификатором узла и подключён к API той же панели.

| Публикация | Проверка | Что получил приёмник |
| --- | --- | --- |
| Ревизия 2 | Один пользователь с активными `qa-direct` и `qa-relay`. Для каждого получен клиентский конфиг из API WebUI | TCP и UDP с внутреннего адреса клиента 10.81.0.3. Для прямого профиля приёмник увидел 192.168.32.2, для цепочки — 172.31.0.2. Интерфейс uplink на входе имел адрес 10.79.0.3 |
| Ревизия 3 в Chrome | Оператор перевёл существующий `qa-direct` на `relay` | После ACK новый поток TCP и UDP вышел через 172.31.0.2. Приёмник вернул ожидаемый адрес и случайный маркер каждого запроса |
| Та же публикация | Оператор добавил `qa-wireguard`. Supervisor создал ключи, запустил адаптер и межсерверный uplink. В панель поступили все три ACK ревизии 3 | Клиент Linux WireGuard с адресом 10.79.0.2 получил ответы TCP и UDP через выход 172.31.0.2 |

В ревизии проб 2 источник применил два подписанных назначения. Пробы TCP от Blackbox проверяли доступность приёмника на стороне выхода по 198.18.253.1:47305 и локального тестового сервиса входа по 198.18.253.1:47307. Видимый из панели отчёт `qa-relay` содержал выбранный путь, `desired=2`, `applied=2`, время последнего измерения, RTT, loss и конкретные идентификаторы узлов. Временное отсутствие ACK текущей ревизии при переходе 2 → 3 давало HTTP 409 при выдаче конфига. После ACK выдача возобновилась. Три полученных файла побайтно совпали с файлами, сгенерированными узлом для своих профилей. Клиент с заменёнными ранее реквизитами ревизии 1 при обращении на действующий адрес и порт прежнего профиля не создал TUN за 15 секунд.

## Повтор проверки трафика

Скачайте профиль через WebUI в приватный файл. На том же rootless Docker хосте передайте действующий проект выхода, ожидаемую сеть SNAT и отдельную сеть для клиента. Временный приёмник помещается в ожидаемую сеть. Стендовому пользователю нужны sudo-права на запуск тестовых сокетов в выделенных сетевых пространствах. Команда создаёт собственные контейнеры с уникальными именами и удаляет их после проверки.

```sh
python3 contrib/deploy/tests/managed_traffic.py --config qa-direct.toml \
  --exit-holder flowqa-exit-network-1 --exit-network flowqa-exit_vpn \
  --client-network flowqa-panel_vpn --network-image "$NETNS_IMAGE" --client-image "$CLIENT_IMAGE"
python3 contrib/deploy/tests/managed_traffic.py --ingress wireguard --config qa-wireguard.conf \
  --exit-holder flowqa-exit-network-1 --exit-network flowqa-exit_vpn \
  --client-network flowqa-panel_vpn --network-image "$NETNS_IMAGE" --client-image "$INGRESS_IMAGE"
```

Активные сценарии и журналы приёмки гостя находятся в `~/flow-accept/lab`. В этом каталоге также хранится приватное состояние тестовых профилей. Публикуются только результаты наблюдений. Для возврата прежнего маршрута опубликуйте сохранённый inventory с текущей базовой ревизией, дождитесь ACK и повторите проверку адреса.

## Старый playbook и перезагрузка гостя

После публикации ревизии 3 в Chrome повторён реальный `site.yaml` с прежним inventory. Контейнеры панели были пересозданы с сохранением БД. После готовности WebUI все три профиля по-прежнему показывали ревизию 3. Новый клиент `qa-direct` передал TCP и UDP на 172.31.0.3, а приёмник подтвердил прежний выбранный выход 172.31.0.2. Журнал прогона гостя — `~/flow-accept/lab/post-play.log`.

После перезагрузки boot ID сменился с `3700ffb0-b4ca-4184-ba3e-5098c6131fac` на `28f54a0b-6083-475b-9bbe-f30381b14ea1`. Сервисы Docker и supervisor, панель, её зарегистрированные узлы, рабочие профили и адаптер WireGuard запустились автоматически. Для тестового TCP-приёмника на стороне выхода первоначально не была задана политика рестарта. После загрузки он оставался остановленным. Только этот вспомогательный контейнер был запущен вручную с `restart: unless-stopped`. Проверка дождалась готовности панели и авторизованной выдачи текущей ревизии. При контрольном чтении свежие отчёты всех трёх профилей показывали ACK 3 и доступность разрешённой связи с ревизией пробы 2; возраст наблюдения составил 16,6 с.

После загрузки SHA-256 выданного native-файла совпал с прежним `30454f1527eb6f8618dae5105c47eb9de6e26ccc9d6b2ead184639f751c4386f`, WireGuard — с `008a83801192ac568f276519bed4538e0a60bea8a17349c7d10adde5102f615e`. С этими файлами отдельные клиенты заново передали TCP и UDP. На приёмниках 172.31.0.3 и 172.31.0.4 подтвердился один выбранный выход 172.31.0.2. Журнал — `~/flow-accept/lab/postboot.log`.
