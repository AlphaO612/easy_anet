# Два профиля на linux/amd64

Прямой профиль подключается к одному серверу. Для цепочки отдельный входной сервер принимает клиентское соединение и передаёт IPv4-пакеты через второй ANet-сеанс на выход. Оба профиля можно выдать одному пользователю. Каждый вход имеет свою пару ключей, UDP-порт и namespace. Контейнеры работают в rootless Docker с доступом к /dev/net/tun. Понадобятся Python 3, OpenSSL, Docker Compose и образы NETNS_IMAGE и SERVER_IMAGE этой сборки. Для входа цепочки нужен также CLIENT_IMAGE. Команды выполняются из корня репозитория.

Соберите отсутствующие образы на сборочной машине, например:

```sh
docker build --platform linux/amd64 -f contrib/docker/Dockerfile.client -t anet-client:chain .
docker build --platform linux/amd64 -f contrib/docker/Dockerfile.netns -t anet-netns:chain .
```

На выходе замените exit.example.org публичным именем узла. Адреса туннелей должны различаться и не пересекаться с Docker-сетями и адресами сервисов.

```sh
export STATE_DIR="$HOME/anet-exit" TUN_SUBNET=10.78.0.0/24 TUN_ADDRESS=10.78.0.2/24 VPN_PORT=4519
python3 contrib/deploy/scripts/init-state.py "$STATE_DIR" exit.example.org "$VPN_PORT" standalone --subnet "$TUN_SUBNET"
docker compose -p anet-exit -f contrib/deploy/compose/compose.yaml up -d
```

Передайте файл client.toml выхода по закрытому каналу на вход в файл $HOME/anet-uplink.toml с правами 0600. Этот ключ принадлежит входному узлу. Один раз добавьте в файл параметры клиента:

```toml
[main]
manual_routing = true
tun_name = "anet-uplink"
```

На входе запустите прямой профиль на UDP 4519 и цепочку на UDP 4520. Здесь SERVER_IMAGE, NETNS_IMAGE и CLIENT_IMAGE должны указывать на образы, доступные в rootless Docker этого хоста.

```sh
export TUN_SUBNET=10.77.0.0/24 TUN_ADDRESS=10.77.0.2/24
export STATE_DIR="$HOME/anet-direct" VPN_PORT=4519
python3 contrib/deploy/scripts/init-state.py "$STATE_DIR" entry.example.org "$VPN_PORT" standalone
docker compose -p anet-direct -f contrib/deploy/compose/compose.yaml up -d

export STATE_DIR="$HOME/anet-chain" VPN_PORT=4520 UPLINK_CONFIG="$HOME/anet-uplink.toml"
python3 contrib/deploy/scripts/init-state.py "$STATE_DIR" entry.example.org "$VPN_PORT" standalone
docker compose -p anet-chain -f contrib/deploy/compose/compose.yaml -f contrib/deploy/compose/chain.yaml up -d
```

Выдайте пользователю client.toml из anet-direct и anet-chain под разными именами. При потере связи с выходом цепочка прекращает передачу. Прямой профиль продолжает работу. При пересоздании namespace запускайте up -d для всего проекта. Храните ключи, конфиги и значения переменных запуска в резервной копии. При запуске Docker после перезагрузки контейнеры восстанавливаются по restart policy. Для запуска пользовательского Docker до входа в систему настройте systemd lingering.

Приёмка запускает три серверных namespace в одной изолированной тестовой сети. Проверяются разные адреса выхода TCP и UDP, потеря uplink и восстановление:

```sh
python3 contrib/deploy/tests/chain.py
```

Для испытания на двух отдельных хостах запустите на выходе `python3 contrib/deploy/tests/chain.py serve-exit /tmp/anet-qa-exit EXIT_IPV4 UDP_PORT`, указав адрес, назначенный хосту, и свободный порт. Скопируйте тестовую директорию /tmp/anet-qa-exit по SSH в приватную директорию на входе. На входе выполните `python3 contrib/deploy/tests/chain.py accept --remote-exit /tmp/anet-qa-exit`. Проба обращается к TCP/UDP echo-сервису в приватной сети выхода и сверяет адрес отправителя с адресом его серверного namespace. По завершении создайте файл /tmp/anet-qa-exit/stop на выходе и удалите тестовые ключи на обоих хостах. Стенд выхода также завершается по тайм-ауту 20 минут.

### Проверенный стенд

22 ноября 2026 года приёмка прошла на двух отдельных VPS linux/amd64 с rootless Docker. Прямой и цепочный профили действовали одновременно. На одном хосте echo получил по TCP и UDP адрес 172.22.0.4 для прямого профиля и 172.22.0.3 для цепочки. Остановка uplink сохранила прямой обмен, локальный echo не получил контрольную датаграмму цепочки. После рестарта uplink оба протокола снова достигли выхода.

В межхостовом испытании версии `2211fa7` вход установил аутентифицированный ANet-сеанс через временный UDP-порт выхода. Обе Docker-сети использовали одинаковые приватные адреса. Тест дополнительно сверял идентификатор удалённого echo-сервиса в каждом ответе TCP и UDP, включая ответы после перезапуска uplink. Измерения относятся к адресу, который наблюдал сервис в приватной сети выхода.

Домашний Debian 13 amd64 проверен отдельным клиентом в Docker через команду `python3 contrib/deploy/tests/chain.py remote-client BUNDLE --python-image PYTHON_IMAGE`. В версии `53b399b` нативный QUIC до одного VPS доставил TCP и UDP на его приватный echo-сервис. Проверены случайные данные, идентификатор echo и адрес источника после NAT. Маршруты IPv4 и IPv6 по умолчанию на домашнем хосте совпали до и после запуска. До второго VPS с того же домашнего подключения оба проверенных транспорта, QUIC по UDP и WebSocket по TCP, завершились тайм-аутом.

В финальном испытании версии `c146aac` домашний клиент одновременно подключался двумя профилями к отдельному входному VPS в РФ. Прямой профиль достигал приёмника на входе, цепочный — приёмника на втором VPS. Проверены TCP, UDP и уникальный идентификатор каждого приёмника. HTTPS-сервис api.ipify.org видел публичный IPv4 входа для прямого профиля и публичный IPv4 второго VPS для цепочки. Во время остановки межсерверного клиента прямой профиль сохранил публичный адрес, а TCP и UDP цепочки перестали достигать приёмника. На входе отсутствовала контрольная датаграмма утечки. После запуска межсерверного клиента оба публичных адреса и оба протокола проверены повторно. Домашние маршруты по умолчанию сохранились.

Отдельный профиль WireGuard подключался к тому же выходу через отдельный постоянный проект входа. QR был декодирован локально и побайтно сопоставлен с выданной конфигурацией. Этот конфиг проверен клиентом WireGuard с домашнего Debian по публичному адресу выхода и DNS-запросу к резолверу из профиля. Импорт в приложение на физическом iPhone в это испытание не входил.

Пользователь подтвердил приёмку на физическом iPhone: подключение по выданному WireGuard QR состоялось, показанный внешний IPv4 совпал с адресом назначенного выходного узла. Постоянный профиль сохранён отдельно от временного стенда.

### Пропускная способность WireGuard через ANet

Для измерения 22 ноября 2026 года использовались отдельные WireGuard peer и ANet-сеанс. Домашний Debian передавал данные по маршруту домашний WireGuard → входной VPS → ANet QUIC → выходной VPS → приватный TCP-приёмник. У каждого VPS один vCPU. Сервер измерения находился только в сети контейнеров выхода. Ключи, MTU WireGuard 1280, TUN, сервер измерения и маршрут сохранялись между сериями. Менялись образы ANet-клиента на входе и ANet-сервера на выходе.

[Скрипт измерения](../tests/throughput.py) работает с одним TCP-потоком. После короткого прогрева выполнены три загрузки и три отдачи. Отправитель писал блоки по 64 КиБ в течение восьми секунд. Скорость рассчитана по доставленным байтам и прошедшему времени у получателя, включая доставку оставшихся в очереди данных. A выполнялась до B.

| Образы | Загрузка, Мбит/с | Медиана | Отдача, Мбит/с | Медиана |
| --- | --- | ---: | --- | ---: |
| A, сборка dev, теги accept | 5,49 / 4,24 / 7,66 | 5,49 | 5,29 / 0,88 / 7,01 | 5,29 |
| B, release, теги stage4-1f7cb32 | 14,40 / 11,99 / 11,68 | 11,99 | 7,24 / 9,31 / 9,73 | 9,31 |

За 37 двухсекундных интервалов средняя загрузка CPU контейнера исходящего ANet-клиента снизилась с 28,8% до 10,1% одного ядра, сервера — с 29,9% до 6,9%. Ограничитель cgroup CPU не зарегистрировал throttling ни в одной серии. На VPS продолжали работу другие процессы. Полученные значения относятся к этому маршруту и Linux-клиенту. Скорость физического iPhone после обновления измеряется на самом телефоне.

Рабочий клиент и сервер затем переведены на те же release-образы. Compose пересоздал только сервисы uplink на входе и server на выходе через up -d --no-deps. Проверены фактические идентификаторы образов контейнеров, прежний ID WireGuard-контейнера, старое содержимое конфигурации WireGuard и выход отдельного авторизованного клиента через рабочий туннель по UDP DNS и HTTPS.

Для такого обновления сначала загрузите образы на оба узла. Сохраните .env рядом с исходным файлом и проверьте конфигурацию командой docker compose config --quiet с теми же проектом и файлами, что использовались при запуске. В .env выхода измените SERVER_IMAGE и примените только server. В .env входа измените CLIENT_IMAGE и примените только uplink. Обновление разрывает межсерверный сеанс. Для отката восстановите сохранённый .env в каждом проекте и повторите те же команды для соответствующего сервиса. После обновления или отката проверьте регистрацию клиента на выходе, ответ DNS и публичный IP через туннель.
