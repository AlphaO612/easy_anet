# Управление входными профилями из панели

Панель хранит опубликованную топологию и отдельно принимает отчёты входов. На входном узле один пользовательский сервис systemd следит за назначениями этого узла. Для каждого профиля он резервирует порт из локального диапазона, создаёт ключи, отдельную сеть и Compose-проект. Для межсерверного перехода используется ANet QUIC. WireGuard и VLESS/TLS могут принимать клиентов перед нативным входом. Для каждого нового uplink приватный ключ создаётся на входе. Выход получает разрешение по отпечатку ключа, UUID выхода и действующей ревизии.

## Однократная подготовка

Используйте Python 3.11+ с cryptography, OpenSSL, пользовательский systemd с lingering и rootless Docker с Compose. Установите панель со сборкой auth и WebUI из этой ветки, PostgreSQL, подписью и мониторингом. В профиле webui включите --probe-management и настройте сбор метрик, в полном профиле эти компоненты входят в состав. Укажите защищённый HTTPS-адрес API, доступный как с хоста агента, так и из контейнера выходного сервера. Для локального агента допустим API на loopback. Скопируйте публичный ключ панели probe-signing/public по доверенному SSH-каналу.

1. Создайте в разделе серверов запись для готового VPS с его адресом и UDP-портом QUIC. Выпустите одноразовое приглашение. Если поле публичного ключа пустое, узел заполнит его при регистрации. Если ключ или порт уже заданы, панель сверит их с локальной идентичностью.
2. На отдельном VPS сохраните одноразовый токен в приватном файле и задайте настройки присоединения. Например, файл join.json содержит следующие поля.

   ```json
   {"api":"https://panel.example/api/v1","node_id":"9ec57585-f086-46fc-b49b-c0721879165c","invitation_file":"/home/deploy/private/invitation"}
   ```

3. Добавьте `--join-panel /home/deploy/private/join.json` к обычной установке standalone. Идентичность и конфиг сервера сохраняются в его каталоге состояния. На внешнем выходе эта установка разрешает назначенные uplink по индивидуальному токену узла. В Ansible используется `anet_join_panel`. Встроенный в установку панели локальный сервер уже получает control_plane при первом запуске.
4. На узлах, которым можно назначать входные профили, подготовьте settings.json. Укажите абсолютные пути к server.toml зарегистрированного узла и к доверенному публичному ключу подписи. Выберите отдельный диапазон портов и IPv4-подсеть клиентского туннеля, отличную от подсетей выходных серверов и Docker. Хост служит клиентским адресом, поле bind задаёт локальный адрес прослушивания.

   ```json
   {
     "api":"https://panel.example/api/v1",
     "node_config":"/home/deploy/private/node/server.toml",
     "signing_public":"/home/deploy/private/panel-public",
     "state":"/home/deploy/private/managed-entries",
     "host":"entry.example",
     "bind":"0.0.0.0",
     "ports":[48000,48031],
     "source":"10.86.0.0/24",
     "dns":"9.9.9.9",
     "images":{}
   }
   ```

   Заполните images неизменяемыми идентификаторами именно этого rootless Docker. Используйте идентификаторы SERVER_IMAGE, NETNS_IMAGE, CLIENT_IMAGE, INGRESS_IMAGE и DNS_IMAGE из вывода `python3 contrib/deploy/scripts/bundle.py load /path/to/bundle anet-easy`. Для VLESS добавьте пути tls_cert и tls_key к доверенной клиентом цепочке сертификатов и закрытому ключу адреса host. Для доменных условий нужен образ DNS_IMAGE. Файлы настроек и каталог state должны принадлежать пользователю rootless Docker. Каталог state должен иметь режим 0700.

5. Установите сервис параметром `--flow-agent /home/deploy/private/settings.json` или переменной inventory `anet_flow_agent`. На уже развёрнутом узле можно выполнить `python3 contrib/deploy/scripts/install-flow-agent.py /home/deploy/private/settings.json`. Панели не нужен доступ к Docker socket. Команду и выбранные каталоги хранит пользовательский unit anet-flow-*.service.

## Выдача, применение и отзыв

В панели опубликуйте межузловую пробу на входе и проверьте её наблюдение в графе. Откройте «Топология профилей» → «Назначить вход и выход». Выберите вход, выход, действующую пробу, внешний IP, пользователя, протокол и стратегию. Для прямого пути выберите один узел в обоих полях. Чтобы добавить запасной выход, добавьте ещё один путь к тому же именованному профилю. Опубликуйте черновик. Сложные условия CIDR, доменов и назначение нескольких групп доступны в редакторе JSON. Для профиля с DNS-условиями задайте dns_path из списка paths, иначе используется первый путь. DNS-запрос к указанному рекурсивному серверу ограничен сроком пригодности пробы этого пути.

Дождитесь отчёта с номером опубликованной ревизии и временем. Узел сверяет подпись, создаёт сервисы и применяет правила. При исчерпании путей подтверждение может содержать решение «передача запрещена». «История решений» показывает до 50 последних смен политики или выбора с наблюдениями проб. Кнопка «Скачать профиль» запрашивает выданные реквизиты текущей ревизии через API администратора. В БД конфиг зашифрован ключом DB_ENCRYPTION_KEY. Сохраните загруженный файл в приватном месте.

«Отозвать» удаляет профиль из черновика. После публикации выдача старого конфига через панель прекращается. Агент снимает проект и освобождает выделенный ему порт. Для ротации идентичности действующего профиля задайте новый UUID в credential_id и опубликуйте. Отключённый от панели вход прекращает пересылку по истечении локальных сетевых аренд. Данные отозванных профилей сохраняются в приватном каталоге для операционного восстановления. Срок хранения архивных ключей задаёт оператор узла.

## Возврат к предыдущей политике

Экспортируйте действующий inventory до изменения. Для отката загрузите прежние paths и profiles в черновик поверх текущей базовой ревизии и опубликуйте. После применения сверьте номер ответа входа и адрес выхода тестового клиента. Документы о восстановлении БД и ключей и об эксплуатации вручную настроенных профилей находятся рядом. [Восстановление](recovery.ru.md), [локальные привязки](flow-routing.md).
