# Восстановление панели и ключей узла

Резервная копия профиля `webui` состоит из логического дампа PostgreSQL и каталога `STATE_DIR` одного момента обслуживания. В каталоге состояния находятся серверный ключ и сертификат, реквизиты уже зарегистрированного узла, ключ шифрования данных auth, параметры подключения к БД и ключ подписи проб. Для `anet-easy` сохраните также файлы, указанные в параметрах входа и uplink, настройки Compose и монтируемые снаружи каталоги. Для управляемых профилей сохраните настройки flow-agent, весь его приватный каталог state с привязками портов и ключами и исходные TLS-файлы VLESS. Для истории метрик и последних применённых проб отдельно сохраните именованные тома metrics, grafana и probe-targets. Для восстановления без доступа к registry сохраните проверенный комплект образов и исходный коммит установщика.

Ниже `source_compose` и `target_compose` обозначают команды `docker compose` с файлами и аргументами конкретной установки, включая её имя проекта, env-файл и образы. Переменная `STATE_DIR` в каждой команде должна указывать на соответствующий каталог узла. Выполняйте команды от пользователя rootless Docker.

### Создание копии

На время копирования завершите изменения из панели и IaC, остановите процессы, которые меняют файлы состояния. Для профиля webui остановите webui и auth. Запишите версии образов, путь к env-файлу и список внешних монтирований вместе с копией. Используйте новое приватное расположение вне `STATE_DIR`.

```sh
set -eu
umask 077
mkdir -m 700 "$BACKUP"
source_compose stop webui auth
trap 'source_compose start auth webui' EXIT
source_compose exec -T db pg_dump -Fc -U anet -d anet > "$BACKUP/database.dump"
tar -C "$STATE_DIR" -cpf "$BACKUP/state.tar" .
(cd "$BACKUP" && sha256sum database.dump state.tar > SHA256SUMS)
source_compose start auth webui
trap - EXIT
```

Копия содержит ключи доступа. Храните её в зашифрованном хранилище с ограниченным доступом. Сверяйте контрольные суммы после передачи через доверенный канал.

### Восстановление в отдельный проект

Выберите новый проект, свободные порты и новые имена томов, включая явно именованный `PROBE_VOLUME`. Используйте отдельную машину или сеть для проверки копии действующего узла. Две копии одного node ID при одновременном подключении к рабочей панели могут затереть статус друг друга. Разверните ту же версию PostgreSQL и auth. На время импорта в новом проекте должен работать только db с пустой БД. Инструменты pg_dump и pg_restore запускаются из одного образа PostgreSQL.

```sh
set -eu
umask 077
(cd "$BACKUP" && sha256sum -c SHA256SUMS)
mkdir -m 700 "$RESTORED_STATE"
tar -C "$RESTORED_STATE" -xpf "$BACKUP/state.tar"
export STATE_DIR="$RESTORED_STATE"
target_compose up --no-build --pull never -d --wait db
target_compose exec -T db pg_restore --single-transaction --exit-on-error \
    -U anet -d anet < "$BACKUP/database.dump"
target_compose up --no-build --pull never -d --wait webui
```

Войдите в новую панель, сравните ID и открытый ключ узла, опубликованную ревизию, историю и конфигурацию существующего клиента. После проверки реквизитов и отключения старого экземпляра запускайте нужные сервисы восстановленного проекта. При ошибке импорта оставьте рабочий проект на прежних портах. Проверьте версию PostgreSQL и контрольные суммы и повторите импорт в пустую БД.

### Проверка

Задайте `SERVER_IMAGE`, `NETNS_IMAGE`, `AUTH_IMAGE` и `WEBUI_IMAGE` из локального комплекта и выполните в корне checkout:

```sh
python3 contrib/deploy/tests/restore.py
```

[Тест восстановления](../tests/restore.py) создаёт два Compose-проекта со случайными именами, отдельными ключами и томами. Он сравнивает содержимое и режимы файлов, проверяет вход с исходным паролем, чтение ревизии и инцидента, расшифровку существующего клиентского ключа через API выдачи конфига и heartbeat со старым токеном. После испытания тест освобождает собственные проекты и тома.

22 ноября 2026 года на Docker Desktop 24.0.6 / Compose 2.23.0 из исходного проекта восстановлена панель во втором проекте с новым томом. Оба проекта использовали PostgreSQL 17 и auth из пакета stage4-1f7cb32 (config ID b31eb513fe9a). Исходный auth, БД и WebUI были остановлены на момент проверки новой панели. Подтверждены исходная ревизия и инцидент, расшифровка клиентского конфига, вход администратора и heartbeat ранее зарегистрированного узла. Каталог состояния сохранил содержимое файлов и их права. Внешние тома мониторинга и перенос на новый VPS в этот прогон не входили.

Повторный прогон `RESTORE_AUTH_IMAGE=anet-auth:flow-accepted python3 contrib/deploy/tests/restore.py` импортировал тот же тип дампа в новый том и запустил миграции при старте нового auth. Ранее выданный клиентский ключ и узловой heartbeat сохранились. Свежий ACK со статусом applied разрешил скачать конфиг. До ACK и после error ACK панель вернула HTTP 409. Повторный applied ACK сохранил одну запись изменения в истории. После публикации удаления профиля GET вернул 404, PUT со старой ревизией — 409. Зарегистрированный выход подтвердил свой uplink, чужая пара ID и токена получила 401, после отзыва проверка на прежнем выходе вернула allowed=false.
